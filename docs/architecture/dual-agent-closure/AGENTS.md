## Dual-Agent hard laws

1. Local and cloud are independent execution and evidence lanes.
2. Transport acknowledgement, workflow state, task result, Gate result, effect result, artifact result, user result, Human Admit and release are separate facts.
3. At-least-once delivery is expected. One observable effect requires an idempotency key, canonical effect identity, effect ledger, target readback, and explicit unknown/reconciliation states.
4. `LOCAL_ONLY` data, secret values, browser/device sessions, personal profiles and machine-local paths never enter portable packets or receipts.
5. API-first is legal only for an exact admitted provider, schema, auth method, endpoint/method set, usage policy and error contract.
6. Browser fallback has a separate, lower evidence ceiling and never inherits API reliability, idempotency, or terms.
7. Shared docs, CRDTs, vector stores, memory and observability projections remain rebuildable context/projection planes, not workflow or transaction authority.
8. Provider names are adapter decisions, not architecture invariants.
9. Disconnect, duplicate, timeout, cancellation, stale result, policy refusal, partial artifact, cleanup failure, compensation failure and unknown external effect remain distinct.
10. Source prose, issue closure, merged mechanism bytes, CI, another host, another provider, or another platform never substitute the required physical/user/release lane.

## Independent Shadow review

The Shadow reviewer must use a context separate from the implementing Worker and ask:

1. Does the issue still protect every selected `DA-Pxx` problem?
2. Did implementation narrow the user outcome without recording the exclusion?
3. Did one lane proxy another: local/cloud, API/browser, provider/provider, transport/task, workflow/Gate, result/effect, artifact/user, test/live, Human/release?
4. Are source, runtime, policy, identity, target, artifact and rollback subjects exact and current?
5. Are failed, stale, cancelled, duplicate, skipped, blocked and superseded attempts still in the denominator?
6. Can every claimed artifact and external effect be independently read back?
7. Are cleanup, residue, cancellation, compensation and restart/reconnect physically observed where claimed?
8. Are licensing and third-party rights explicitly admitted for the exact release composition?
9. Is one convergence owner responsible for shared indexes/status/release?
10. Is the next Local Handoff executable on an available host without relying on chat history or a private bundle?

A Shadow disagreement stops convergence as `CONTESTED`, `UNKNOWN`, `REPLAN_REQUIRED`, or another exact blocked state. It does not silently rewrite implementation or promote a weaker lane.

## Stop conditions

Stop mutation and update the owning issue/Local Handoff when any of these occurs:

- parent PR #176 moved, closed, merged, or its route bytes changed;
- current branch no longer contains the expected parent ancestry;
- source problem, user outcome, interface owner, path lease, provider, policy, data class, effect class or exact subject changes;
- a required cross-repository contract is absent or stale;
- a semantic conflict has no deterministic declared winner;
- a provider, credential, network, device, signed-in session, local service or Human decision is unavailable;
- the same failure signature reaches three materially different attempts;
- a required negative control cannot turn red;
- cleanup/residue, target readback, artifact readback or rollback becomes unknown;
- licensing or usage terms are missing for a mandatory release subject;
- the proposed change would edit a parent/convergence-owned queue, lock, status, release or generated path.
