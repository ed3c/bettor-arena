> Source under review: **《黑客松 AI 開發：SKILL.md 與 MCP》**. This document is a requirement/hypothesis source, not repository truth. Numeric adoption, success-rate, latency, market-share, YC-preference, and product-scale claims in the PDF are **not admitted** unless independently verified.

## 1. Verdict

`bettor-arena` already implements the **modular control-plane form** of most useful PDF ideas, but it deliberately does **not** copy several unsafe or incorrect PDF assumptions.

The integration shape is:

```text
PDF concept
  ↓ translate / correct
Portable Skill procedure         ← skills-shared immutable release
  ↓
Bettor Skill binding + module composition
  ↓
Default-deny stateless MCP surface
  ↓
Typed host-owned execution request
  ↓
Disposable execution environment / provider adapter
  ↓
Independent assertions + proof/control/mutation
  ↓
Subject-bound receipts
  ↓
Human Admit / release / rollback
```

The architecture therefore separates **instruction**, **tool transport**, **execution**, **verification**, and **release authority** instead of treating one `SKILL.md`, Promptfoo run, or MCP server as the whole governance system.

## 3. Corrections to the PDF model

### 3.1 Stateless MCP is not “a TypeScript switch function”

The PDF example named `executeStatelessMCPTool()` is a tool executor pattern, not sufficient proof of an MCP Server. Bettor keeps transport/protocol, public command contract, execution carrier, and module closure separate.

```text
MCP transport/request
→ explicit external policy
→ generated public tool
→ typed carrier
→ module public port
→ bounded execution
```

### 3.2 Promptfoo/evals are not the runtime safety layer

The PDF places evals visually in the request path. Bettor separates:

```text
offline / CI eval
    verifies a candidate before admission

runtime enforcement
    schema + policy + allowlist + subject identity + bounded execution
```

A benchmark cannot authorize a production mutation.

### 3.3 “Self-healing” must be bounded

Bettor translates self-healing to:

```text
named failure
→ bounded repair policy
→ same hard gate rerun
→ preserved previous error
→ stop at budget
```

It rejects retry-until-pass because that destroys denominator integrity and hides defects.

### 3.4 A cloud sandbox is a provider, not the architecture

E2B, Firecracker, Daytona, local process isolation, WASM, and future runtimes fit behind a provider interface. The architecture must remain valid if one provider disappears.

### 3.5 Product/adoption numbers from the PDF are not evidence

Claims such as “98% success”, specific user counts, market share, sub-150ms latency, or YC adoption remain external hypotheses. Bettor documents `PASS`, `FAIL`, `ABSENT`, `NOT_IMPLEMENTED`, `NOT_EXERCISED`, and `SKIPPED_BY_POLICY` instead of importing illustrative numbers.

## 7. Modular integration verdict against the PDF

### Already stronger than the PDF

- typed module ownership instead of one monolithic MCP server;
- default-deny exposure instead of implicit tool availability;
- immutable subject identity instead of mutable checkout execution;
- independent proof/control/mutation instead of a single benchmark score;
- bounded Micro loops instead of unbounded self-healing;
- Human Admit separated from model tools;
- providers and cloud sandboxes treated as replaceable adapters;
- instruction, runtime, evidence, origin, browser and release states remain distinct.

### Still missing for a full physical claim

- convergence of the portable Skill execution stack into current `main` (#53);
- exact-head green checks for provider admission (#56);
- physical filesystem/network isolation provider canary;
- current-subject Claude Code + Codex CLI execution receipts;
- live browser/provider canaries where required;
- cross-environment GitHub/Forgejo equivalence receipt for the named release;
- first external consumer release acceptance and Human Admit.
